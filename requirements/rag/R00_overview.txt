DVRK TECHNICAL RETRIEVAL (RAG) - REQUIREMENTS OVERVIEW
======================================================

Status
------
IN PROGRESS. Tasks R01, R02, R03, R04 and R08 are built and measured. R05, R06, R07, R09 and R10
are specified below and not built. A task has its own file once it is built.

Purpose
-------
A retrieval system over the engineering knowledge of the da Vinci Research Kit: its documentation,
its issue threads, its change log and its configuration schemas. It answers the questions an
operator or a service engineer has in front of the robot (what does this error mean, how is this
calibrated, what is this configuration key, did this change in a release) with the sources that
support the answer. The agents of this repository (vxagent) call it as a tool. It is a separate
package (vxrag) that imports nothing from the agents, runs as its own service, and can be moved to
its own repository unchanged.
It is a research demonstration on public text. It is not maintained by the dVRK project, and an
answer from it is not a substitute for the documentation it cites.

Relation to the earlier retrieval project
-----------------------------------------
The earlier project (deepwise_rag) retrieves similar patient cases from clinical records. Its
ideas are all kept here: an authoritative store with derived, rebuildable indexes; a retrieval
unit that is a thing a person would point at, not a text chunk; every tokenizer, embedding
model, chunking rule and fusion rule as a configuration among competitors; a selection policy
fixed before the numbers are seen, with a held-out set scored once; answers that cite and are
checked against their evidence, or abstain; access decided inside retrieval; change-driven
re-indexing; and release gates.
What is different is the kind of text and therefore every job task:

    Earlier project                              Here
    clinical case = patient + procedure time     a documentation section, a thread's replies, one
                                                 release note, one configuration key
    typed laboratory values and diagnosis codes  identifiers: topic names, file names, config
                                                 keys, error strings, kept whole (R03)
    prose reports                                reStructuredText with code blocks, labels and
                                                 cross-references; JSON Schemas; threads (R01)
    no record from after the query date          no page written for the other hardware
                                                 generation; no fact from a release the site
                                                 does not run (R05)
    published similarity labels, reviewers       labels built by code from the links and replies
                                                 the authors themselves made (R08)
    patient-level access control                 public sources for everyone, a site's own notes
                                                 for that site only; who wrote a reply (R07)
    answer compares cases                        answer is a procedure: ordered steps, commands
                                                 quoted exactly, where it applies (R06)

Data (all public, downloaded by scripts/fetch_sources.py, none committed)
-------------------------------------------------------------------------
Documentation    jhu-dvrk/dvrk-readthedocs at commit 3b231b2, reStructuredText only: 234 files,
                 0.74 MB. The repository is about 0.9 GB of images and slides; the script makes a
                 sparse, blob-filtered checkout of the text.
Issue threads    jhu-dvrk/sawIntuitiveResearchKit and jhu-dvrk/dvrk-ros through the public GitHub
                 API: 161 threads (138 closed), 205 replies, fetched 2026-11-19. Most threads were
                 opened by the maintainers themselves (enhancement notes and bugs); about a fifth
                 were opened by other users. Author names are not stored, only the author's
                 association with the repository and whether the author opened the thread.
Change log       CHANGELOG.md of sawIntuitiveResearchKit at commit 7435458: 19 releases.
Schemas          The 18 JSON Schemas of the dVRK configuration files, with the description of
                 every property. Several documentation pages only embed these schemas, so the
                 schemas are the only place their content exists as text.
Licences         The documentation and the source repository state no licence. The text is used
                 locally to build indexes and is not redistributed. Evidence files contain unit
                 identifiers and short query excerpts, not pages.

Models
------
Embedding models nomic-embed-text and bge-m3, and (for R06) qwen3, all served by Ollama on this
machine. The embedding client refuses any endpoint that is not local.

Job tasks
---------
R01 Sources and ingestion          built    adapters for four kinds of source, a reStructuredText
                                            reader, validation report, idempotent re-ingestion
                                            with removal of what disappeared upstream
R02 Chunking                       built    three strategies behind one function; chunks belong
                                            to units; a code block is never cut
R03 Lexical and dense indexing     built    two tokenizers, BM25, two local embedding models, a
                                            persistent embedding cache
R04 Retrieval strategies           built    lexical, dense and reciprocal-rank fusion as named
                                            configurations; filters applied inside the search
R05 Applicability                  planned  The site profile (hardware generation, installed
                                            release) filters and annotates results. Renames are
                                            read from the change log ("console" became "system"
                                            in 2.4.0) so a question in old terms finds new pages
                                            and the answer says which term applies to the site.
R06 Grounded procedure answers     planned  A token-budgeted evidence bundle; a structured
                                            answer of ordered steps, each with citations; every
                                            command, file name, key and number in the answer must
                                            occur word for word in a cited unit; a statement of
                                            which generation and release it applies to;
                                            abstention when the evidence does not answer.
R07 Trust, access and injection    planned  Official text ranks above maintainer replies, and
                                            those above other replies, and an answer says which
                                            it relies on. A site's own service notes are a
                                            private collection filtered inside retrieval and
                                            inside the cache. Thread text is untrusted: planted
                                            instructions must not change an answer.
R08 Evaluation protocol            built    labels from links and replies, three query
                                            categories, development and test splits, nDCG,
                                            recall, MRR, paired bootstrap, a written selection
                                            policy, the test set scored once and locked
R09 Service and operations         planned  HTTP API and CLI; index versions that are built,
                                            validated, activated and rolled back; incremental
                                            sync from upstream by commit and by thread update
                                            time; latency and cache metrics; release gates.
R10 Use by the agents              planned  search_docs, search_threads and search_by_log_line
                                            as agent tools over HTTP with timeout and retry; the
                                            agents' grounding guard checks cited unit ids.

Design rules
------------
1. The store is authoritative. Indexes are derived, carry the hash of the corpus they were built
   from, and can be rebuilt from the store alone.
2. The unit of retrieval and of evaluation is a section, a thread's question, a thread's replies,
   a release-note category or a configuration key. Chunks are an indexing detail.
3. Nothing is selected in code. A tokenizer, a model, a chunking rule and a fusion rule are
   names in a configuration, compared on the same queries.
4. The more complicated option must earn its place: it replaces the simpler one only when the
   paired-bootstrap interval of the difference lies above zero and it fits the latency budget.
5. The test queries are scored once, for the configuration the policy selected.
6. Fail loudly: an embedding that is not finite, a count that does not match, a cross-reference
   that points nowhere and a duplicate identifier are reported, not worked around.
7. Text never leaves the machine. Embedding and generation use local models only.
8. Measured results are written by scripts/rag_experiments.py into verification/ and are never
   typed into these files.
