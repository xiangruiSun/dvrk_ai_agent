TRAINING-DATA FINDER (vxfind) - OVERVIEW OF THE JOB TASKS
==========================================================

Read this file first. It says what is being built, for whom, who builds which part, and where
each job task is written down. The job tasks themselves are in requirements/system/ (the
engineering team) and requirements/eval/ (the evaluation, built from nothing by one intern).

The earlier job tasks of this repository (fifteen agent tasks around a surgical-robot console and
eleven retrieval tasks over robot documentation) were reviewed with the team's mentor. The
verdict: several of them were not what a company with clients would staff. They describe an
agent for a robot nobody is paying for yet, and they evaluate with labels derived from document
structure, not from what a user asked. They are kept, with their code and their evidence, under
requirements/archive/. What follows replaces them as the main line of work.


1. The problem
--------------
A new team member's first real task is to train or fine-tune a model. Before they can, they
have to find data. The team's training data is a catalog of about 100,000 "tables" (datasets of
recorded robot episodes), each with an address (URL), a schema (columns: cameras, joint states,
actions), a size, an owner, and sometimes a description. The catalog is the pain:

  - Most tables say nothing about themselves. About 5 in 100 have a description a person wrote.
  - Nearly one in five is scratch work with a name like "test_3" or "record-tmp".
  - Tables come in families of near-identical copies (the same recording session uploaded as
    fifty tables). The largest family has nearly two hundred members.
  - The robot is spelled in more than 1,200 ways.
  - Tables are deleted, made private, renamed to another owner and changed, every day. Any list
    of tables is out of date by the time it is read.
  - Using a table for training needs a mentor's approval, and some tables must not be shown to
    people outside one group at all.

Today a newcomer asks around, gets a few addresses in chat, finds that two are dead, and spends
days before the first training run. The mentor's time goes into answering the same question for
every newcomer.

The product: an assistant the newcomer asks in plain words ("SO-101 pick-and-place, a few
hundred episodes, with a wrist camera"). It returns at most ten tables with working addresses
and one sentence each on why they fit, says honestly when nothing fits, and files the request
for the mentor's approval when asked. Behind it: retrieval over the catalog (RAG), a language
model that decides which tables to show, and live checks through MCP servers, because the
retrieval index and the table list are always behind the real world.

How we know it works is the hard part and the focus of this repository. "It returned ten tables"
is not a result. Which ten, compared to what, judged by whom, how sure, and would we notice if
it got worse next month: that is the evaluation, and it did not exist. It is built here from
zero.


2. Who uses it
--------------
  newcomer   a new engineer (ours, or a client's engineer being onboarded to the platform).
             Asks for data, reads descriptions, asks for access. May see only what their groups
             may see.
  mentor     approves or refuses requests to use a table for training. Never approves their own.
  the team   reads the evaluation reports and decides what ships.

There are no real users in this repository. Where a result depends on user behaviour, a script
plays the user and the report says SCRIPTED. Where a policy is needed (who may see what), it is
DECLARED for the project and labelled so. Where a fault is needed to test a reaction (a table
that vanished), it is INJECTED and labelled so. The catalog itself is real.


3. The data: a real catalog standing in for the company's
---------------------------------------------------------
The catalog is the public Hugging Face Hub's collection of robot-learning datasets in the
LeRobot format: about 100,000 tables from 9,000 owners, describing 17 million episodes and 6
billion frames, roughly 50 TB of data and video by the tables' own declaration. It has every
property listed in section 1, at real scale, and it changes daily (the measured figures are in verification/REPORT.md, "Write path"; the ones
here are rounded). Two snapshots a month apart
give real growth and real change; the live site gives real deletions, moves and gating.

What is downloaded is metadata only (dataset cards and listings, about 2 GB), never the data or
the video. Nothing downloaded is redistributed: data/ is not in git. See data/README.md.

Three views of the same catalog, deliberately at three ages, as in production:

  search index       built from the older snapshot (about one month old)
  catalog database   loaded from the newer snapshot (the system of record, hours to days old)
  the site           asked live, per table, at answer time

Two front ends over the same parts: a fixed pipeline (the steps above in code, at most one model
call) and an agent (a tool-calling loop that decides the steps itself, can take follow-up
questions and file an access request). Both are checked by code before a person sees the answer.


5. The team and who owns what
-----------------------------
A senior engineer leads four to five engineers for eight months. One intern (a new graduate,
six months) owns the evaluation. The split below is how the job tasks are written.

  Lead (senior)          architecture, the serving contract, capacity plan, release decisions,
                         review of every design below. Owns S6 and the roadmap.
  Engineer A (data)      sources and the catalog record (S1); the Spark write path (S2).
  Engineer B (search)    the index and the read path: analyzers, hybrid retrieval, fusion,
                         collapse, rerank, select (S3).
  Engineer C (platform)  the MCP servers, their schemas, authentication, rate limits (S4).
  Engineer D (agent)     the agent, its tools, the answer check, the fixed pipeline (S5).
  Engineer E (serving)   API, logging, the feedback log, deployment and operations (S6, with the lead).
  Intern (evaluation)    everything under requirements/eval/: E00-E12. Starts with nothing:
                         no queries, no labels, no metrics code, no judge, no gate.

The intern does not tune the system. They build the instrument that says whether a change by
engineers A-E made things better, and they are the person who says "we cannot tell" when the
instrument cannot.


6. Roadmap (months 1-8)
-----------------------
  Month 1   S1: sources, record model, first Spark job on one snapshot. S3: first index, BM25.
            Eval E01: read 100 real catalog rows and 50 hand-run searches, write the failure
            taxonomy. E03: metrics library with tests.
  Month 2   S2: embeddings with cache, index versions and alias switch. S3: kNN and RRF.
            Eval E02: the four query sets, splits, the locked test set. E04: pooling and the judge.
  Month 3   S3: family collapse, scratch demotion, "understand". S4: MCP servers with schemas.
            Eval E05: judge calibration against computed truth; the hand-label sheet. E06: first
            full ablation and the rule that chooses the serving configuration.
  Month 4   S5: the agent and the answer check; the fixed pipeline. S2: incremental sync.
            Eval E07: reasons (groundedness) and "nothing fits" (abstention). E11: planted faults,
            power, agreement between query sets.
  Month 5   Self-test inside the team (dogfood). S6: API, logging, feedback log.
            Eval E08: freshness, before and after the live check. E09: access and leak tests.
            E10: agent trajectories.
  Month 6   Open to the first newcomers. S6: capacity tests, growth plan.
            Eval E12: feedback -> candidate cases -> labelled cases; the release gate in CI.
  Month 7   Open to all teams. Weekly evaluation report; the gate blocks releases.
  Month 8   Hand-over: runbook, on-call, what the evaluation cannot see and how to find out.

The intern's six months are months 1-6 above; E00 lays their plan out week by week.

JSON file. Nothing is typed in by hand. A first run that exposed a wrong design is kept.


8. What was read to design this (and what was taken from each)
--------------------------------------------------------------
Table and dataset discovery at companies
  Uber, QueryGPT: an intent step before retrieval narrows the tables searched; specialised
    agents per step. Taken: "understand" as a separate, measurable stage (S3 R6).
  LinkedIn, SQL Bot: embedding retrieval over table descriptions; tables without a description
    are a first-order quality problem; a step that checks the model's table names against the
    catalog. Taken: generated summaries for every table (S2 R4), ids never taken from the model (S5 R4).
  Pinterest, text-to-SQL: table summaries are indexed, the model picks K of N retrieved; offline
    evaluation is a sanity check and real usage decides. Taken: select stage (S3 R9), E12.
Benchmarks and methods for evaluating retrieval and RAG
  TARGET (table retrieval benchmark): recall@k of the right table drives everything downstream.
  TREC pooling and Cranfield practice: depth-k pools, unjudged documents, bias against systems
    that were not pooled. Taken: E04.
  UMBRELA and Thomas et al. (LLM relevance judgments, used in the TREC 2024 RAG track): a
    graded prompt, one document per call, can stand in for assessors for system ranking; less so
    for absolute scores. Taken: the judge prompt and its limits (E04, E05).
  ARES: a small human-labelled set (about 150) corrects an automatic judge statistically. Taken:
    the hand-label sheet as a required deliverable (E05).
  RAGAS / TruLens "RAG triad": context relevance, groundedness, answer relevance as separate
    measurements. Taken: E07 measures reasons separately from retrieval.
  "Who Validates the Validators" (criteria drift): rubrics change as people grade; version the
    prompt, keep every judgment. Taken: E04 R6.
  Work on synthetic queries (e.g. arXiv 2508.11758): rankings from synthetic benchmarks can
    disagree with human ones. Taken: E11 measures the agreement instead of assuming it.
  Error-analysis-first evaluation practice: look at failures before choosing metrics. Taken: E01.
Search engineering
  Elasticsearch documentation on RRF and linear retrievers, rank_constant and rank_window_size.
    Taken: S3 R5; fusion is done by the caller because the engine's own RRF is a paid feature
    (verified on the installed engine, see REPORT.md).
  Interleaving (team-draft) for online comparison. Taken: E12, as the next step once there is traffic.
Protocol
  Model Context Protocol specification: tools with inputSchema and outputSchema, structured
    results, annotations. Taken: S4.


9. Glossary
-----------
  table        one dataset in the catalog: an id (owner/name), an address, a schema, a size.
  family       tables that are near-identical copies: same owner, same name pattern, same schema.
  scratch      a table named like test, temporary or debugging work.
  need         what a person asks for, in their words.
  pool         the union of the top results of several systems for one need; what gets judged.
  qrels        judgments: need, table, grade.
  dev / test   the two halves of every query set. Choices are made on dev. Test is scored for
               the final table and the gate.
  serving      the search configuration that answers users, chosen on dev by a written rule.
  live check   asking the hosting site about a table at answer time.
  gate         the automated decision whether a change may ship.
