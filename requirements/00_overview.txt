DVRK AGENT TOOLS - REQUIREMENTS OVERVIEW
========================================

Status
------
DESIGN. These files state what will be built and how it will be verified. No code exists yet and
no result has been measured. Every "Code" section lists planned modules; every "Verification"
section lists the command that will produce the evidence.

Purpose
-------
Role-scoped AI agent tools for operating and servicing a da Vinci Research Kit (dVRK) in a
surgical-robotics lab: an edge node next to the robot controller, used by the operator who runs
trials and by the engineer who calibrates and repairs the system, with a safety lead who approves
anything that moves or changes a limit, and a remote support team that sees fleet health without
seeing the lab's data. Everything here runs on public data with a local model and a kinematic
twin of the arm. It is a research demonstration. It is not connected to a robot, it is not a
medical device, and nothing in it is a statement about clinical use.

How to read these files
-----------------------
One file per job task. Each file states the job, the numbered requirements, the planned code, the
real data it runs on, and the command that verifies it. Measured results are never typed into
these files: they will be written by scripts/verify.py into verification/*.json and summarised in
verification/REPORT.md.

Relation to the earlier project
-------------------------------
The earlier project (ai_agent_tools_deepwise) covers the same concept list for a chest CT service.
There the agents read records and draft text that a radiologist signs. Here the agents sit beside
a machine that moves: state changes while the model is thinking, actions take seconds and can be
cancelled, a physical step cannot be retried or assumed still true after a restart, and the
knowledge base is engineering documentation, support threads, configuration and telemetry.
Every concept is kept; every job task and the skill it exercises is different. Three tasks close
limits the earlier project stated about itself: plan steps that could not use another step's
output (task 04), an MCP server reachable only over stdio (task 07), and a fleet view across
sites that was not built (task 13).

Robot
-----
No robot and no ROS installation is assumed. The default backend is a kinematic twin written in
Python from the real dVRK kinematic and instrument files: it integrates commanded poses, applies
joint limits and reports measured and setpoint poses, which is what the dVRK software's own
kinematic simulation mode does. It has no contact, no needle and no camera. A second backend
speaks the CRTK command set over ROS 2 for use on a lab machine; it counts as verified only for
the runs actually made there. The interface is the same for both (task 14).

Model
-----
qwen3:14b and qwen3:4b served by Ollama on the local GPU. The language model is never inside the
control loop. The on-prem profile blocks any outbound call that is not to an allowed host.

Design rules that apply to every task
-------------------------------------
1. The model never produces a number that reaches the robot. No pose, increment, gain or limit
   comes from model text. The model chooses a validated procedure and its typed parameters;
   targets are computed by code and checked by the safety filter (task 09 R5).
2. A target outside the envelope is rejected, never clipped. The rejection is an observation.
3. An observation has an age. A tool that moves the arm refuses to act on a state older than the
   freshness limit, and the model must look again (task 01 R6).
4. Motion is never retried automatically. A read may be retried; a motion that did not finish is
   reported with the measured pose and the reason, and a person or a recovery procedure decides.
5. After a restart nothing physical is assumed. Each step declares what must be true before it
   runs and checks it by observation (task 03 R6).
6. Authorization is decided from the signed-in principal: role, site, and action tier (observe,
   simulate, actuate). It is enforced in the tool executor on every call and again in HTTP.
7. Anything that moves the arm needs an operator approval bound to the current state. Anything
   that changes a limit or a configuration needs the safety lead, who cannot be the requester.
8. Text from logs, support threads and documentation is data. It is never treated as an
   instruction, and this is tested with planted instructions (task 07 R8).
9. Every model call, tool call, action, event and guard is traced on the same clock as the robot
   telemetry.
10. Verification runs on real data with the real model. Where a fault or an outcome is injected
    it is labelled as injected in the evidence and in the report.
