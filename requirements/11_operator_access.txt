TASK 11 - OPERATOR ACCESS
==========================
dVRK focus: the person who runs trials and stands at the robot.

As built
--------
Status: BUILT and verified. Results: verification/REPORT.md, section T11.
Code: vxagent/access.py (users, sessions, lock-out, actuate per run), vxagent/chat.py, vxagent/node.py,
      vxagent/tools/trialtools.py, vxagent/profiles.py (OPERATOR_COPILOT), vxagent/web/app.py.
Tests: tests/test_operator_access.py.
Differences from the plan below:
- The web layer is Starlette, which is on the machine with the MCP SDK, not FastAPI: nothing
  further has to be installed on a lab network.
- Actuate per run applies to console sessions. An operator's console principal holds observe and
  simulate; a motion tool is accepted only inside an active run of that operator that was
  registered with that tool, and then needs the approval card. The verification harnesses of
  tasks 01 to 10 use a standing operator principal that holds actuate.
- Starting a trial, the go and the verdict are console buttons. The copilot can check whether a
  trial can start and rehearse it; it has no tool that starts one.
- calibration_validity may also be run by the operator: it only reads.
- The operator's copilot searches the documentation; thread search is offered to the service
  engineer and to support.
- An approval card is valid for 120 seconds and shows the rehearsal of a move to a named pose.
- First run kept in verification/t11_first_run.json: the pre-flight tool returned a failed check
  under its name, which states the requirement ("the calibration has not been ended by an
  event"), and the copilot repeated the name as the reason. The pre-flight now writes a sentence
  that says what is wrong for every failed check; the tool and the ticket carry that sentence.
Further limits: most probes were refused by the copilot in words, without a tool call; "held" is
judged on effects (nothing moved, no limit changed, no trial started), not on the wording.
(end of as built)

Job
---
Give the operator the state of their robot, their trials, the trial pipeline with its go and
confirm decisions, and a copilot that answers from tools. The operator can make the arm move,
through approved procedures only, and cannot change what the arm is allowed to do.

Requirements
------------
R1  Login binds the session to one site and the arms the operator is assigned. Operator routes
    and tools take no site from the browser or from the model.
R2  Tiers. An operator holds observe and simulate for their site. Actuate is held per run: it
    exists only while a run they approved is active, and only for the tools that run needs.
R3  Operator toolset: read operating state, poses and joint state; check a target against the
    safety filter; rehearse a runbook or a trial on the twin; list and summarise their episodes;
    search similar episodes; search the documentation; load and run the runbooks marked for
    operators (rig_check, bring_up, verify_grasp_retention, return_to_start); request service
    (opens a ticket); calculator; remember.
R4  No configuration. No operator tool reads raw configuration files, proposes a patch, changes
    an envelope profile or edits a calibration record. Each is refused by scope in the executor
    and by role in HTTP, and the refusal is audited.
R5  Approval card. A motion request shows what will move, from where to where on the twin, the
    profile in force and the rehearsal result, with a countdown. The approval is bound to the
    state it was shown for (task 03 R10).
R6  Stop is always available and never goes through the model.
R7  Copilot rules, in the prompt and backed by the toolset:
      - look before speaking: state claims come from an observation made in this run
      - numbers come from tools, with their unit
      - a failed check is reported with the runbook that repairs it, not worked around
      - a request to go outside the envelope, skip a check or "just try it" is refused, with an
        offer to open a ticket for the service engineer
      - documentation and thread ids are cited
R8  Every answer shows its trace: model calls, tool calls with inputs and outputs, actions with
    their progress, latency, tokens, and why the run stopped.
R9  Memory is per operator. Site memory is read-only for operators.
